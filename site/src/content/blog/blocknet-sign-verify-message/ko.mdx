결제 없이 Blocknet 메시지 서명으로 주소 제어를 보여 주세요. 이 안내는 2026년 10월 27일 확인한 공식 CLI v1.2.0과 core v0.22.0을 따릅니다. 명확한 챌린지를 준비하고 의도한 지갑에서 서명한 뒤 전체 주소, 메시지, 서명을 함께 검증합니다.

## Blocknet 메시지는 어떻게 서명하고 검증하나요?

<Answer>
전체 지갑을 불러와 주소를 확인하고 sign으로 합의한 문구에 서명하세요. 주소, 정확한 메시지, 결과 서명을 검증자에게 공유하세요. 검증자는 verify로 세 값을 함께 검사하고 메시지가 요청한 목적과 새로운 챌린지에 맞는지 확인합니다.
</Answer>

## 서명 메시지의 의미 합의하기

어느 주소가 누구에게 어떤 작업을 위해 제어를 입증할지 구체적으로 정하세요. [결제 증명](/ko/blog/blocknet-payment-proof/)은 거래 상세를 입증합니다. 메시지 서명은 계정 주소 확인처럼 서명 키 제어가 질문일 때 유용합니다. [지갑 안내](/ko/blog/blocknet-wallet-for-mining/)는 서명할 지갑 생성과 열기를 설명합니다.

검증자가 이 요청에 새로운 예측 불가능한 챌린지를 제공하도록 하세요. 서비스나 수신자와 의도한 작업을 식별할 맥락을 넣고 필요하면 만료를 합의하세요. 이는 앱 규칙이며 서명 검사기는 최신성, 만료, 일회 사용을 자동 강제하지 않습니다. 검증자가 메시지를 요청과 비교하고 챌린지 사용을 기록해야 합니다.

## 의도한 전체 지갑 열기

터미널에서 실행 중인 mainnet core에 연결하세요.

```sh
blocknet attach mainnet
```

대화형 셸에서 지갑을 불러와 주소를 확인하세요.

```text
load
address
```

의도한 파일을 선택하고 요청되면 클라이언트에서 잠금을 푸세요. 같은 컴퓨터에 여러 파일이 있어도 전체 주소를 검증자가 예상하는 주소와 비교하세요.

[검토한 core](https://github.com/blocknetprivacy/core/blob/5a0a5b510c1dce46f4eeb12c33a291052e44e7b3/api_handlers.go)는 지갑의 지출 개인 키로 서명합니다. [보기 전용 지갑](/ko/blog/blocknet-view-only-wallet/)은 이 작업을 할 수 없습니다. 전체 지갑은 의도한 컴퓨터에 두세요. 검증자는 결과 서명과 공개 정보만 필요합니다. 서명 절차에 송금이나 지갑 파일 내보내기는 필요하지 않습니다.

## 서명 전 정확한 문구 준비하기

전체 요청을 읽고 명시된 목적이 의도한 것인지 확인하세요. 공식 클라이언트는 한 줄을 읽고 앞뒤 공백을 제거하며 빈 메시지나 1024바이트 초과를 거부합니다. 바이트 제한이므로 비ASCII 문자는 한 글자에 여러 바이트일 수 있습니다. 짧고 명확한 한 줄을 쓰고 제출한 정확한 문구를 보관하세요.

검증자에게 전달할 때 대소문자, 문장부호, 내부 공백을 바꾸지 마세요. 편집기나 채팅 앱이 따옴표나 복사 내용을 바꿀 수 있으므로 검증 실패 시 실제 메시지를 비교하세요. 로그인이나 계정 흐름에서는 서비스의 문서화된 챌린지 형식을 따르세요. 검증자는 발급한 특정 요청을 검사해야 하므로 문구를 알리지 않고 고치지 마세요.

## 공식 셸에서 메시지 서명하기

대화형 셸에서 프롬프트를 시작하세요.

```text
sign
```

클라이언트가 텍스트를 묻습니다. 합의한 한 줄을 붙여 넣고 Enter를 누르세요. 성공하면 16진수 서명을 출력합니다. 모든 문자를 보존해 전체를 복사하세요. [클라이언트 구현](https://github.com/blocknetprivacy/blocknet/blob/948af4de8b7a3e3cddc86a329c7d2d003cb3fd6b/attach_wallet.go)은 메시지를 지갑 서명 엔드포인트로 보냅니다. 이 작업은 거래를 만들거나 전파하지 않습니다.

전체 주소, 정확한 메시지, 서명을 각각 별도 값으로 주세요. 서명을 메시지나 주소로 오인하지 않도록 명확히 표시하세요. 복구 시드, 개인 키, 비밀번호는 비공개로 유지하세요. [시드 안내](/ko/blog/seed-phrase-explained/)는 복구 자료를 설명하며 그 어떤 것도 서명 확인자에게 보내는 증거에 포함하면 안 됩니다.

## 상대방은 어떻게 서명을 검증하나요?

실행 중인 호환 core와 공식 셸 검증 프롬프트를 사용합니다.

```text
verify
```

전체 주소, 정확한 메시지, 16진수 서명 순서로 입력하세요. [셸 참조](https://github.com/blocknetprivacy/blocknet/blob/948af4de8b7a3e3cddc86a329c7d2d003cb3fd6b/docs/reference-core.md)가 이 순서를 문서화합니다. 검증에는 지갑을 불러올 필요가 없으므로 서명자의 지갑을 가져오거나 개인 키를 다루지 않고 검사할 수 있습니다.

검토한 클라이언트는 조합이 검증되면 `Signature is VALID`, 아니면 `Signature is INVALID`를 표시합니다. 입력 형식 오류는 별도 결과입니다. 재시도 전에 모든 필드를 확인하고 원본 증거를 보존하세요. 메시지나 주소가 요청과 다르면 제공한 값에 수학적으로 유효해도 차이를 해결하세요.

## 요청 맥락에서 성공 해석하기

유효한 서명은 제공 주소에 인코딩된 지출 공개 키에 대해 메시지를 검증합니다. 법적 신원이나 잔액, 결제 발생을 입증하지 않습니다. 결제 질문에는 [발신 기록](/ko/blog/send-receive-blocknet/), [탐색기 조회](/ko/blog/blocknet-explorer-guide/), 거래별 증명을 사용하세요. 모든 유효한 서명을 영수증으로 보지 말고 실제 질문에 답하는 증거를 고르세요.

수락 전에 챌린지의 최신성과 의도한 수신자를 확인하세요. 유효한 메시지와 서명을 복사해 같은 쌍을 다시 제시할 수 있습니다. 일회 승인이 필요한 서비스는 직접 규칙을 강제해야 합니다. 메시지에 적힌 만료도 검증자가 확인해야 의미가 있습니다. 이런 검사가 암호학적 유효성을 합의한 작업에 연결합니다.

## 명확한 검증 기록 유지하기

감사 기록이 필요하면 주소, 정확한 메시지, 서명, 요청 맥락, 결과를 함께 보관하세요. 검증 시각은 서명자가 적은 시각과 별도로 기록하세요. 서명 텍스트를 받은 누구나 읽고 복사할 수 있으므로 무관한 개인정보는 넣지 마세요. 합의한 채널로 의도한 검증자에게 공유하세요.

채굴 지급을 받는 지갑이어도 셰어와 지급 기록은 [풀 추적](https://bntpool.com/blog/ko/track-your-miner-on-bntpool/)이 제공하며 메시지 서명은 대체하지 않습니다. [노드 안내](/ko/blog/run-blocknet-node/)는 공식 셸에 필요한 core를 설명합니다. 합의한 검사가 끝나면 서명 접근은 전체 지갑에 두고 결과 확인자에게는 공개 검증을 사용하게 하세요.

取引鍵と受取アドレスを取引と照合して、特定のBlocknet支払いを検証します。本ガイドは2026年10月27日に確認した公式CLI v1.2.0とcore v0.22.0に基づきます。証明の生成、正しい項目の共有、チェーン状態と併せた結果の読み方を説明します。

## Blocknetの支払いを証明するには？

<Answer>
送信ウォレットを開き、取引IDを指定してproveを実行し、得られた取引鍵を対象の検証者に渡します。検証には鍵、取引ID、受取アドレスを使います。鍵が有効か確認し、次にそのアドレスに一致する出力と金額を調べます。
</Answer>

## 証明したい支払いから始める

送信記録から完全な取引IDを保存します。[送信ガイド](/ja/blog/send-receive-blocknet/)は公式クライアントのID表示場所を、[エクスプローラーガイド](/ja/blog/blocknet-explorer-guide/)は取引と収録ブロックの探し方を説明します。公開IDで送金を特定できますが、通常のページは特定アドレスへの非公開の支払い金額を明かしません。

どの受取アドレスと支払い記録を確認するか合意します。省略名や画像ではなく、その支払いの完全なアドレスを使います。名前で支払った場合は実際に使ったアドレスを保持します。証明は特定の受取確認や受取人との疑問解決に役立ちますが、現実の人物の身元を証明するものではありません。

## 送信ウォレットで取引鍵を生成する

ターミナルから稼働中のmainnet coreに接続します。

```sh
blocknet attach mainnet
```

対話シェルで送信ウォレットを開き、記録を確認します。

```text
load
address
history
```

目的のファイルを選び、必要ならクライアントでロックを解除します。初期設定は[ウォレットガイド](/ja/blog/blocknet-wallet-for-mining/)を使ってください。

プレースホルダーを完全な取引IDに置き換え、シェルで実行します。

```text
prove <txid>
```

[確認したクライアント](https://github.com/blocknetprivacy/blocknet/blob/948af4de8b7a3e3cddc86a329c7d2d003cb3fd6b/attach_wallet.go)は64文字の16進数IDを受け付け、返された取引鍵を表示します。coreはローカルチェーン上の取引を探し、導出した鍵が公開鍵に一致するか確認します。送信したウォレットを使ってください。生成操作は別の支払いを作りません。

## どの情報を共有する？

合意した経路で取引ID、返された取引鍵、対象の受取アドレスを共有します。取引鍵はこの取引専用です。復元シード、支出鍵、ウォレットのパスワード、ウォレット全体の閲覧秘密鍵は非公開に保ちます。検証者に必要なのは証明項目であり、開いたウォレットや復元資料へのアクセスではありません。

これは支払い情報の意図的な開示です。鍵と受取アドレスにより、一致する出力、金額、その取引の復元可能なメモを識別できます。証拠が必要な相手と共有してください。[メモガイド](/ja/blog/blocknet-encrypted-memos/)は支払い注記を説明します。証明を共有する前に内容を考慮してください。共有済みの鍵はコピーできるので、受取人と合意した非公開経路を使います。

## 文書化されたcore APIで検証する

[公式API](https://blocknetcrypto.com/api)には、読み込み済みウォレットもBearerトークンも不要な公開証明検証エンドポイントがあります。管理下のノードを優先してください。以下を非公開の作業フォルダーに `proof.json` として保存し、3つの仮文字列を実際の証明項目に置き換えます。フィールド名は変えません。

```json
{
  "txid": "REPLACE_WITH_TRANSACTION_ID",
  "tx_key": "REPLACE_WITH_TRANSACTION_KEY",
  "address": "REPLACE_WITH_RECIPIENT_ADDRESS"
}
```

そのフォルダーからノードのAPIアドレスへファイルを送ります。

```sh
curl -H "Content-Type: application/json" --data-binary @proof.json http://127.0.0.1:8332/api/verify-proof
```

ローカルポートが異なる設定なら変更してください。Windows PowerShellでは `curl.exe` を使います。[ノードガイド](/ja/blog/run-blocknet-node/)はcoreの起動を説明します。この要求は証拠の確認であり、コインを送りません。リモートサーバーを使うと、提出した項目が運営者に開示されます。

## 鍵の有効性と受取人の一致を分けて読む

まず `valid` を見ます。trueは取引鍵と公開鍵が一致することを示します。次に `outputs` を見ます。`match` がtrueの項目は指定した受取アドレスに属します。`total_matched` はその金額の合計です。有効な鍵でも、指定アドレスがその取引を受け取っていなければ、一致出力はゼロになることがあります。

APIの金額は最小単位で、100,000,000単位が1 BNTです。BNT建て請求書と比較する前に合計を換算してください。早い段階で丸めず、整数の全桁を保持します。返されたメモを期待する記録と照合してください。収録と承認はノードまたはエクスプローラーで別に検証します。証明結果だけでは請求書の全額支払いも、現在の資金の使用可能性も分かりません。

## 不一致は元の記録で解決する

無効な鍵なら、完全なIDと鍵を送信者の元の出力と比較します。有効な鍵で受取人の一致がない場合は、使った完全なアドレスを再確認します。生成時に取引が見つからない場合は、ノードのネットワークとチェーン進行を調べます。確認した生成エンドポイントはチェーン上の取引を必要とします。ローカルチェーンが遅れていれば[同期ガイド](/ja/blog/blocknet-wallet-not-syncing/)に従ってください。

プール払出では、自分の受取ウォレットはプール取引を作った送信ウォレットではありません。[プール追跡記録](https://bntpool.com/blog/ja/track-your-miner-on-bntpool/)と入金履歴から始め、送信者の証明は実際の送信者から取得します。確認した生成エンドポイントでは、coinbaseのマイニング報酬にも送信者証明はありません。これらの違いを踏まえ、対象の支払いに合う証拠を選びます。

## 目的と結果を証明と共に保存する

取引ID、受取アドレス、関連する支払い参照情報、検証結果を非公開記録にまとめます。確認したネットワーク、ノード、時刻も残します。目的に必要な支払い情報だけを保持してください。証明を受け取った人は他人の結果画像に頼らず、自分で検証を繰り返せます。

[署名付きメッセージ](/ja/blog/blocknet-sign-verify-message/)は別の目的を持ち、特定のメッセージについてアドレスの署名鍵を管理していることを示します。取引固有の証拠には支払い証明を、合意した所有確認にはメッセージ手順を使います。[閲覧専用ガイド](/ja/blog/blocknet-view-only-wallet/)は、支出を承認できなくても閲覧権限が重要な秘密情報である理由を説明します。各証拠を、それが答える問いに結び付けてください。

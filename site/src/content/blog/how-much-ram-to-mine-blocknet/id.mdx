Pilih thread CPU yang muat dalam memori tersedia. Panduan ini membahas alokasi 2 GiB, pengaturan otomatis seine v0.2.26, dan pemeriksaan saat pengaturan manual gagal mengalokasikan memori. Perbandingan chip dan hashrate terukur ada di [panduan perangkat keras](/id/blog/blocknet-mining-hardware-hashrate/). Contoh di sini adalah hitungan memori, bukan pengukuran kinerja.

## Berapa RAM yang dibutuhkan setiap thread?

<Answer>
Setiap thread CPU memerlukan arena memori Argon2id 2 GiB. Sisakan ruang untuk sistem operasi, aplikasi, dan penambang. Mulai dengan pengaturan otomatis seine yang mempertimbangkan memori tersedia dan sumber daya CPU. Jumlah thread manual harus muat dalam memori yang benar-benar tersedia ketika penambangan dimulai.
</Answer>

GiB adalah satuan biner: 2 GiB sama dengan 2.147.483.648 byte. Arena dipakai ulang antarahash; setiap hash selesai tidak menghabiskan 2 GiB tambahan secara permanen. Lebih banyak thread serentak membutuhkan lebih banyak arena. [Penjelasan Argon2id](/id/blog/argon2id-proof-of-work-explained/) membahas kebutuhan memori kerja ini.

## Bagaimana menghitung anggaran thread?

Kalikan jumlah thread CPU dengan 2 GiB. Tabel ini tidak mencakup sistem dan overhead lain. Gunakan untuk menghitung arena; pilih jumlah nyata berdasarkan memori tersedia dan throughput terukur.

| Thread CPU | Hanya memori arena |
|---|---|
| 1 | 2 GiB |
| 2 | 4 GiB |
| 4 | 8 GiB |
| 8 | 16 GiB |
| 16 | 32 GiB |

Empat thread membutuhkan arena 8 GiB, sehingga perlu lebih dari 8 GiB tersedia untuk sisa proses dan sistem. Jika Anda sengaja menyisihkan 4 GiB dari komputer 16 GiB, sisa 12 GiB secara hitungan memuat enam arena. Ini pilihan anggaran, bukan janji bahwa enam thread memberi hashrate terbaik.

Periksa memori tersedia saat aplikasi sehari-hari terbuka melalui Task Manager Windows, Activity Monitor macOS, atau alat Linux. Mesin virtual atau container dapat memiliki jatah lebih kecil daripada host. Gunakan batas efektif tersebut; RAM yang diiklankan host tidak otomatis tersedia di lingkungan terbatas.

## Bagaimana seine memilih thread otomatis?

Untuk menjalankan CPU saja pertama kali, jangan tetapkan jumlah thread. Jalankan perintah ini dari folder hasil ekstraksi Linux atau macOS. Di Windows, gunakan opsi yang sama dengan executable di PowerShell. [Panduan awal](/id/blog/how-to-mine-blocknet/) menjelaskan unduhan dan alamat penerimaan.

```sh
./seine --backend cpu
```

Pada v0.2.26, penentuan ukuran dan tuning otomatis mencadangkan 5% dari total RAM efektif secara bawaan, selain memperhitungkan memori yang terpakai. Sumber daya CPU juga membatasi jumlahnya. Batasi rentang tuning dengan nilai maksimum:

```sh
./seine --backend cpu --cpu-autotune-max-threads 4
```

Empat adalah contoh batas atas, bukan pengaturan universal. Tuner dapat memilih lebih sedikit thread. Pantau jumlah terpilih dan hashrate rata-rata di [dasbor](/id/blog/seine-dashboard-explained/). Tuning mengukur konfigurasi nyata; tunggu stabil sebelum menilai perubahan dari fluktuasi singkat.

## Kapan jumlah thread perlu ditetapkan?

Tetapkan jumlah untuk anggaran khusus atau konfigurasi yang dapat diulang. Contoh ini memilih dua thread CPU: 4 GiB untuk arena ditambah memori lain.

```sh
./seine --backend cpu --threads 2
```

`--threads` menonaktifkan pemilihan otomatis biasa kecuali Anda juga mengaktifkan tuning secara eksplisit. Ini menggantikan kebijakan cadangan otomatis, jadi sisakan ruang sendiri. Pemeriksaan memori tetap berlaku. Jumlah yang muat dalam RAM terpasang bisa melebihi memori tersedia setelah aplikasi lain berjalan.

Ubah satu pengaturan setiap kali. Catat thread, RAM tersedia, dan hashrate rata-rata pada beban sebanding. Untuk kembali otomatis, hapus argumen thread tetap dan override tersimpan. [Referensi konfigurasi v0.2.26](https://github.com/zpalmtree/seine/blob/v0.2.26/docs/guides/configuration.md) menjelaskan pengaturan tersimpan dan baris perintah.

## Apa yang diperiksa setelah kesalahan alokasi?

Bedakan pesan tentang batas efektif, memori tersedia, atau alokasi halaman besar eksplisit. Pemeriksaannya berbeda. Tutup aplikasi yang tidak diperlukan, kurangi thread, dan mulai ulang dengan ruang untuk penggunaan desktop normal.

Pada container atau mesin virtual, periksa memori yang dialokasikan selain host. Jatah 1 GiB tidak memuat arena 2 GiB. Memperbesar swap tidak mengubah kebutuhan arena; rencanakan memori fisik yang cukup tersedia bagi proses.

Jika memilih `--cpu-page-mode large` atau `--cpu-page-mode large-1g`, pastikan kumpulan halaman cadangan yang diminta tersedia. Mode eksplisit memerlukan backing tersebut. Ikuti [panduan huge pages](/id/blog/huge-pages-blocknet-mining/) atau kembali ke pemilihan halaman otomatis untuk membangun konfigurasi dasar yang berjalan. Ubah halaman dan thread secara terpisah.

## Apakah memori GPU masuk anggaran CPU?

Pada NVIDIA diskret, arena GPU berada di VRAM. Thread CPU tetap memakai RAM sistem. Hitung keduanya terpisah saat CPU dan GPU menambang bersama; VRAM kosong bukan tambahan RAM arena CPU. [Panduan NVIDIA](/id/blog/mine-blocknet-nvidia-gpu/) membahas konfigurasi dan lane GPU.

Pada Apple Silicon, CPU dan GPU berbagi unified memory. Jangan menghitung kapasitas itu dua kali untuk beban lain. Ikuti [panduan Mac](/id/blog/mine-blocknet-on-mac/) untuk konfigurasi CPU yang didukung. Kapasitas menentukan apa yang muat; throughput terukur menentukan konfigurasi terbaik pada mesin Anda.

## Apa yang diperiksa sebelum membiarkan penambang berjalan?

Pastikan thread sesuai anggaran, aplikasi responsif, dan share diterima terus masuk. Alokasi lebih besar saja tidak membuktikan kinerja lebih baik. Pertahankan konfigurasi sesuai beban Anda, lalu gunakan [panduan pelacakan pool](https://bntpool.com/blog/id/track-your-miner-on-bntpool/) untuk memastikan pekerjaan terbaru tercatat pada alamat penerimaan.

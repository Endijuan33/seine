Understand what Faraday is intended to change and which preparation belongs to a wallet user, node operator or miner. This guide separates the announced network plan from the software you can use today. It follows the [official Faraday overview](https://blocknetcrypto.com/#faraday), checked on October 26, 2026, and gives you a practical way to follow the eventual release instructions.

## What is the Blocknet Faraday upgrade?

<Answer>
Faraday is Blocknet’s planned network upgrade. According to blocknetcrypto.com, Faraday would introduce post-quantum spend proofs, full-chain spend privacy and changes intended to speed up node synchronization and wallet scanning. It would upgrade the existing chain and include a wallet-guided move to a new coin format. Development and review are ongoing.
</Answer>

## Which features are planned for Faraday?

The official Faraday plan proposes hash-based proofs for spending and ML-KEM for payment detection. These are parts of Faraday’s proposed post-quantum design. Faraday also aims to broaden the set of outputs that can hide a spend from the current ring of 16 to the full chain. The [privacy guide](/blog/blocknet-privacy-features/) explains the mechanisms used on today’s network.

The same overview describes faster node synchronization, faster wallet scanning and a revised VEIL atomic-swap design as Faraday goals. These are announced directions, not measurements from a released Faraday build. Read each feature together with its release status. A design overview explains the destination; the eventual release notes will identify the supported software and operating steps.

## When is Faraday expected to activate?

The published plan targets activation around February 16, 2027, near the first anniversary of the first block. It then describes a one-year period for moving coins, with the old format closing around February 16, 2028. The official page explicitly marks the dates as planned rather than final. Keep that qualification attached whenever you share the schedule.

Use the timeline to organize updates and reminders, then return to the official source as activation approaches. An article date, a calendar reminder or a screenshot is not confirmation that the network has activated. Check the latest announcement for the actual activation conditions, supported versions and migration availability. The [client’s upgrade notice](https://github.com/blocknetprivacy/blocknet/blob/948af4de8b7a3e3cddc86a329c7d2d003cb3fd6b/README.md) also points readers to the planned transition.

## How would existing coins move to the new format?

The plan keeps Blocknet on the same chain and retains its history. Existing coins would need a move into the new format. The official overview says the wallet would scan, display the fee and perform the move after your confirmation. This is a future workflow: this article does not provide a migration command or ask you to send a payment now.

The proposed deadline matters: coins left in the old format after the migration window would no longer be spendable. Follow the final wallet instructions within the announced window and verify completion in the wallet. Keep the [recovery backup](/blog/seed-phrase-explained/) secure throughout. A backup preserves recovery information; it does not replace the required migration of coins under the planned rules.

## What should wallet users do before the release?

Know which wallet application and version you use, where your backup is stored, and where that application publishes official releases. The [wallet guide](/blog/blocknet-wallet-for-mining/) covers creating a wallet and finding its receiving address. Check your backup procedure before you need it, without entering recovery words into a website or sharing them in a support conversation.

When a migration-capable release is announced, read its instructions before confirming any action. Review the operation, destination if shown and fee in the actual wallet. The [transaction fee guide](/blog/blocknet-transaction-fees/) explains today’s preview and change accounting; it does not specify the future Faraday migration fee. Use the new wallet’s documented workflow for that operation rather than repurposing an ordinary send example.

## What should node operators prepare?

Node operators should track the release that implements the announced network rules and its activation instructions. Keep an inventory of the running core version, network, data directory and services that depend on it. The [node guide](/blog/run-blocknet-node/) explains the present installation and status checks. Read future upgrade notes alongside that inventory so you know which process needs an update.

Plan the maintenance interval around any wallet, explorer or mining service using your node. A core restart affects its API clients as well as its network connection. After an update, check the running version, peers and chain progress using the supported tools. The goal is a verified node on the intended network, with dependent services connected again, rather than only a downloaded archive.

## What does the plan mean for miners?

The official Faraday overview proposes a lighter proof of work as part of its faster-sync design. That statement does not specify a published seine configuration, future hardware ranking or future hashrate. Continue to distinguish current mining instructions from upgrade preparation. Today’s [Argon2id guide](/blog/argon2id-proof-of-work-explained/) describes the existing algorithm; future mining instructions should come from the actual compatible releases.

For a pool setup, follow both the miner’s release instructions and the pool’s announced transition procedure. The [bntpool getting-started guide](https://bntpool.com/blog/mine-blocknet-on-bntpool/) covers the current connection flow. After an instructed upgrade, verify that the intended backend is hashing and fresh shares are accepted. A running process alone is not enough to show that it is working with the pool’s current jobs.

## Keep a short upgrade record

Maintain one record with your application versions, the official announcement link, the date you last checked it and any action still required. Separate node updates, miner updates and wallet migration because they have different completion checks. This makes the plan easier to follow across several computers without treating one successful software update as completion of every task.

Revisit that record when the project publishes a release or revises the schedule. Confirm the final activation and migration dates directly, then record the result of each completed step. Faraday coverage will be most useful when it stays tied to those announcements. Until then, use the existing wallet and mining guides for current operations and this page to understand the proposed transition.
